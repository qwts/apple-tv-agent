# Release pipeline maintenance

`Release bundles` validates PRs touching bundle inputs, supports manual builds, and builds version tags. It uses pinned PyInstaller 6.22.2 in one-folder mode: the runtime and native libraries travel with the executables. Native hosted builds avoid cross-compilation. The frozen router keeps the two CLI entry points and routes the bounded JPEG subprocess back into its own bundled executable instead of assuming `sys.executable` is a Python interpreter. This follows [PyInstaller's runtime distinction](https://pyinstaller.org/en/stable/runtime-information.html).

Build locally with `uv sync --locked --extra screen --group release`, then `uv run --no-sync python tools/release/build_bundle.py --target macos-arm64` (substitute the native target). Check the archive with `uv run --no-sync python tools/release/check_bundle.py release-dist/ARCHIVE`. Output and build intermediates are ignored by Git. CI uploads these archives, downloads them on fresh jobs and runs the same checks with an empty PATH for the bundled process. The checker itself uses Python only as a test harness. Both commands, resources, dynamic imports and the actual worker subprocess are checked without LAN/vault writes.

## Version and publication

`pyproject.toml` is authoritative; the runtime version in `src/apple_tv_agent/__init__.py` must match. Change both and regenerate `uv.lock` in a reviewed PR. Versions use `major.minor.patch` with optional `aN`, `bN` or `rcN`. A tag must exactly equal `v` plus that version. Tag/version mismatch fails before any bundle build. Do not move a published tag or replace its assets.

Before enabling publication, configure a repository tag ruleset restricting creation/update/deletion of `v*` tags to release maintainers. Configure the `release` environment with reviewer/deployment restrictions where your GitHub plan supports them. Merely naming an environment in YAML does not configure protection. The workflow itself always creates a draft and never publishes one. PR and manual builds have read-only repository permissions; only the tag-triggered draft job receives contents write, after all native archive and Python package jobs succeed. No self-hosted runner is used. Jobs have timeouts; PR reruns cancel obsolete work.

After reviewing a version commit, a maintainer creates and pushes its version tag. CI assembles exactly four native archives, a wheel, an sdist, `SHA256SUMS` and `PROVENANCE.json` into a draft. Preview versions are marked prerelease. Inspect the draft's asset list and validation results before manually publishing through GitHub. Creating a tag or publishing a release is not performed by a PR build.

Stable version tags are rejected until `release-gates.json` records that exact version and `passed` for all four OS/architecture targets. Set those fields only in a reviewed change with linked native pairing/reconnect/control, cleanup and compatibility evidence under #1/#10/#18/#30. The gate file is a maintainer assertion, not an automatic substitute for hardware tests. Preview downloads must retain explicit untested-platform limitations. There are no publisher signing credentials configured: Mac builds are ad-hoc signed, Windows/Linux unsigned. Publisher signing/notarization is a follow-up before claiming trusted signed distributions; do not inject private signing material into PR jobs.

## Failure and recovery

A missing target, checksum mismatch or failed smoke check prevents the draft job. Fix code in a PR and choose a new version if a tag already represents a public release. A failed run before draft creation may be rerun for the unchanged tag. Draft creation/upload failure can leave a partial private draft; inspect it and remove only that unpublished draft manually before rerunning. The script refuses existing releases and never clobbers assets, deletes a release or makes a partial release public. The publication job checks the exact asset set and hashes again.

Build identity is recorded in each archive with component versions and license notices. Checksums and JSON provenance are not signed attestations, and byte-for-byte reproducibility is not claimed. The Linux build baseline is Ubuntu 22.04; native Linux keyring and TV validation remains separate from headless CI. The release workflow's native archive matrix complements the existing Python 3.12/3.14 package matrix.
